# 安全登录、会话和登录日志切换

此版本新增服务端认证，不是单独的登录页样式补丁。前端 `authMode: server-v1` 与数据库必须一起发布。不要仅推送页面后遗忘数据库步骤。

## 已实现

- 私有账号、会话、90 天登录日志；`anon` 和 `authenticated` 无直接表权限，只有经过会话校验的 RPC 可读取。日志仅店长可查，客户端不能删除或伪造成功记录。
- 旧密码由服务端验证；第一次成功登录后升级为 bcrypt（先对密码 SHA-256 编码以避免 bcrypt 的 72 字节截断）。新密码至少 10 字符，最多 128 字符；改密验证当前密码并撤销旧会话。
- 账号事务锁与会话版本避免延迟退出覆盖新登录。同浏览器重复登录复用令牌；不同设备成功登录替换会话。前台恢复与公开广播只触发服务端验证。
- 后台“登录记录”提供账号、结果筛选和游标分页；记录时间、结果、原因、网关转发 IP、User-Agent 和设备指纹，不记录密码、哈希或令牌。
- 输入错误密码每账号 10 分钟最多 8 次失败；有转发 IP 时每 IP 10 分钟最多 40 次失败。网络错误不显示“异地登录”。

## 顺序与权限

使用仓库内 `scripts/academy-auth-rollout.mjs`，只在可信本地终端配置 `SUPABASE_ACCESS_TOKEN`。激活还需要 `SUPABASE_SERVICE_ROLE_KEY`。密钥不得写入源码、提交、截图或发到对话。默认站点为本项目 GitHub Pages，可用 `AUTO_OFFICE_SITE_URL` 指定实际发布地址。

1. `node scripts/academy-auth-rollout.mjs prepare`
   创建私有结构与 RPC，导入当前账号，保留姓名、ID、权限和旧密码兼容材料。原账号文件不变，服务保持未启用。导入后核对账号数量、店长及员工名单。初始化阶段重复执行不覆盖不同内容；账号有变化会停止。
2. 完成 `npm ci`、`npm test`、`npm run build`、`npm run check`，发布前端。应安排短暂切换窗口：新页面已部署但数据库未激活时会显示服务尚未启用。
3. `node scripts/academy-auth-rollout.mjs activate`
   校验线上认证脚本版本；冻结旧账号/会话路径的匿名读写；再次核对源账号未变化；启用私有认证；以管理员身份把旧公开凭据文件替换为不含凭据的停用标记，并逐个验证公开下载结果。该操作不会删除员工账号或图片标注。所有旧登录需要重新登录一次，不导入曾经公开的旧令牌。
4. `node scripts/academy-auth-rollout.mjs status`，并通过真实店长账号检查登录、新密码修改、日志筛选、标注前后台切换，以及另一设备登录后的退出行为。

线上桶 `cloud-files` 已确认是 public，旧对象策略允许公开操作。因此只增加 SELECT RLS 不能阻止公开下载，激活阶段必须清理旧对象中的凭据。不要把整个共享桶改成私有，否则其他图片/内容链接可能失效。

## 失败处理

- 准备阶段保持旧服务可用，新增私有结构与旧文件互不覆盖。导入后源文件改变会停止切换；应核对新账号/权限后再安排迁移，不能强行覆盖。
- 激活前的临时冻结失败时，脚本仅在确认尚未启用新认证后撤销本次新增的冻结策略。
- 新认证已启用但旧对象清理失败时，保留保护策略并重试 `activate`，流程支持继续清理。不要把客户端改回旧认证，也不要重新公开私有凭据。
- 账号、密码等真实数据不在仓库备份；私有账号表是迁移后的权威数据。对数据库使用受控备份，不把凭据导出到公开文件。

## 限制

这是账号认证和登录记录的保护，不等于已完成整个应用所有业务表/图片桶的授权改造。`academy_progress` 等现有业务数据权限仍需独立治理。日志从启用后开始，不能补造过去的登录证据；网关 IP、User-Agent、设备指纹是排查线索，不能单独证明身份。客户端离线操作、被请求校验拒绝的畸形输入与未进入 RPC 的网络请求不在这份登录日志中，应结合 Supabase Gateway/Storage 日志核查。

公开过的旧密码哈希可能已被复制，迁移无法收回历史副本。应在关闭旧凭据路径后，引导员工通过新入口修改密码。旧 SHA-256 兼容材料在用户成功登录或改密后移除。
